ACTUALIZACIÓN / HOSTING Y COMUNICACIÓN LOCAL

El dominio da la dirección.
El hosting permite recibir los datos.

El equipo reporta una verificación de JavaScript que impide subir datos desde la ESP32 y menciona InfinityFree. Su plan gratuito documenta ese bloqueo para solicitudes automatizadas. La recepción de imágenes necesita una API compatible con dispositivos.

Comprar sólo un dominio no elimina el bloqueo

Un dominio registrado en Hostinger puede apuntar a distintos proveedores. Si sigue apuntando al alojamiento que exige la verificación del navegador, la ESP32 seguirá encontrando esa barrera.

La API debe vivir en un alojamiento que admita solicitudes HTTPS autenticadas sin ese desafío. El dominio propio es opcional para empezar: primero puede probarse con la dirección que proporcione el servicio elegido.

Hostinger: elegir según el código real

Puede evaluarse para alojar la web y su API, pero el producto contratado debe admitir los lenguajes, bibliotecas y recursos necesarios. Registrar un dominio no incluye automáticamente ese servidor.

Su documentación sitúa Python en VPS y admite Node.js en determinados planes. Eso no garantiza que cualquier plan ejecute el modelo exportado: hay que probar compatibilidad, memoria y procesamiento antes de contratar.

Conservar la interfaz

La ESP32 envía directamente a una API externa. La web existente consulta esa API con los permisos adecuados; sus PHP también pueden hacer llamadas salientes. Un proxy que sólo reenvíe al PHP bloqueado no resuelve el problema.

Migrar el alojamiento

Web y API pueden trasladarse a un servicio compatible. La IA podría alojarse allí o en un proceso separado. La elección espera la URL, los programas y el modelo; todavía no hay un plan de hosting seleccionado.

HC-06: una alternativa para el tramo local

Puede evaluarse Arduino → UART → HC-06 → Bluetooth clásico → ESP32-CAM. El módulo no da internet. Requiere una variante de ESP32 compatible con SPP y pruebas de distancia, firmware y funcionamiento conjunto con cámara y Wi-Fi. Si el montaje permite cablear las placas, UART con adaptación de niveles es otra opción.

Estado: propuesta pendiente de información del equipo. No se ha contratado dominio o hosting ni se ha conectado la estación a un backend real. La alimentación solar requiere revisar la referencia de la placa, regulación, carga y batería.

02 / QUÉ SIGNIFICA WI-FI + HTTPS

Wi-Fi lleva la cámara a la red.
HTTPS lleva los datos al servicio.

Son funciones diferentes. Tener Wi-Fi no significa que la cámara ya esté conectada a la página. Hace falta programar qué envía, a qué dirección, cómo se identifica y qué respuesta espera.

A

Wi-Fi: salir de la huerta

La ESP32-CAM se conecta a una red Wi-Fi de 2,4 GHz con su nombre y contraseña. El router le da acceso a internet; la señal debe llegar al lugar donde está instalada.

La placa tiene radio Wi-Fi, pero necesita un router con conexión. Si no existe esa red, puede evaluarse un router celular con cobertura y plan de datos.

B

HTTPS: entregar el contenido

Ya conectada, la placa abre una conexión cifrada con una dirección del servidor y envía una solicitud. Por ejemplo: una imagen JPEG acompañada por el identificador de captura y las mediciones.

El servidor comprueba quién envía, recibe los datos y responde. La ESP32 debe validar el certificado TLS del servidor; no basta con escribir «https» en la dirección.

SEGUÍ EL RECORRIDO

La ESP32-CAM se conecta al router

El firmware usa el nombre y la contraseña de la red. La placa obtiene una dirección local. Estar conectada al Wi-Fi es sólo el primer paso: todavía debe comprobar que puede llegar al servidor.

Si falla aquí: revisar señal, credenciales, alimentación y acceso a la red.

La conexión la inicia la estación

La ESP32 envía solicitudes hacia el servidor. La página consulta ese mismo servidor. En este diseño no hace falta abrir puertos del router ni publicar la IP local de la cámara. Las órdenes regresan en una respuesta o mediante consultas periódicas de la placa.

03 / CÓMO LLEGAR A LA WEB QUE YA TIENEN

La página necesita una puerta de entrada.

Esa puerta es una API: direcciones del servidor preparadas para recibir imágenes y datos, ejecutar tareas y devolver resultados. Enviar una foto a la dirección de inicio de la página no crea esa integración.

Si su alojamiento ya ejecuta código

Si admite un backend, se pueden añadir allí las rutas de recepción y consulta. Después hay que comprobar que ese entorno también soporte el modelo y el procesamiento continuo, o conectarlo a un servicio que sí lo haga.

Si sólo publicaron HTML, CSS y JavaScript

La página puede conservarse. Se añade un backend aparte y se configura la web para consultar su API. Si usan dominios distintos, el backend autoriza el origen de esa página mediante CORS.

Esta página en angelszs.site explica la propuesta. El servidor receptor de su estación todavía debe definirse con la URL, el código y el alojamiento de su proyecto.

Rutas y valores ilustrativos: no son servicios activos de esta página.

La estación envía una captura

POST https://api.su-proyecto.example/api/estaciones/huerta-01/capturas
Authorization: Bearer CLAVE_DE_ESTA_ESTACION

Contenido multipart:
  imagen: captura.jpg
  captura_id: huerta-01-arranque7-000042
  temperatura_c: 25.4
  humedad_pct: 68

El servidor acusa recibo

HTTP 202 Accepted
{
  "captura_id": "huerta-01-arranque7-000042",
  "recibido": true,
  "procesamiento": "pendiente"
}

«Recibido» no significa «animal reconocido». La clasificación y el conteo pueden completarse después.

Después, cada parte consulta lo que necesita

  • ESP32-CAM: consulta el estado y las órdenes de su estación; entrega al Arduino el estado del semáforo y confirma las órdenes aplicadas.
  • Página web: consulta resultados y últimas imágenes; envía órdenes mediante una sesión autorizada.
  • Servidor: guarda capturas o sus referencias, clasificaciones y eventos; un mismo identificador de captura reenviado no debe generar otra visita.

La credencial de la estación tiene permisos limitados. Las claves administrativas de la base de datos no van en la placa ni en el JavaScript de la página.

04 / DE UNA IMAGEN A UNA VISITA

Reconocer y contar son tareas distintas.

  1. 01

    Capturar

    La ESP32 obtiene imágenes con una frecuencia que debe ajustarse a la duración de las visitas, la señal y el consumo. Una frecuencia muy baja puede perder animales que pasan rápido.

  2. 02

    Clasificar

    El servidor ejecuta el modelo y devuelve clase y confianza. Si lo entrenaron en Teachable Machine, hay que revisar la exportación y probar su ejecución en ese servidor.

  3. 03

    Decidir si hay una nueva visita

    Ver una abeja durante varios fotogramas no significa varias visitas. Hay que definir presencia, salida, confianza y tiempos. Varios animales simultáneos pueden requerir detección y seguimiento, además del clasificador.

  4. 04

    Guardar y mostrar

    Se registra el evento y se actualiza el conteo. La web muestra los resultados y su hora de actualización; el semáforo usa los mismos umbrales y período de conteo.

¿Qué hace el botón «Iniciar»?

Guarda una orden en el servidor. La estación la recibe, activa el monitoreo y confirma. La página debe mostrar «pendiente» hasta recibir esa confirmación.

¿Qué pasa al cerrar la página?

La estación y el servidor continúan trabajando si están activos, alimentados y conectados. Ejecutar toda la IA sólo dentro del navegador no cumple esa autonomía.

05 / QUÉ CONSERVAR Y QUÉ COMPLETAR

Primero integrar lo que ya existe.

Elementos para la integración propuesta
ElementoFunción y condición
ESP32-CAMCaptura y Wi-Fi. Confirmar variante, memoria, alimentación y pines disponibles antes de añadir otra placa de comunicación.
Arduino UnoPuede conservar el control de los LEDs. Si ya obtiene mediciones o conteos válidos, los comparte con la ESP32 mediante un protocolo acordado.
Enlace UART y adaptación de nivelesComunica las placas con tierra común y adaptación apropiada entre 5 V y 3,3 V. No conectar una salida de 5 V del Uno directamente a una entrada del ESP32.
Red Wi-Fi con internetRequiere cobertura en la estación. Sin red disponible hay que resolver la conectividad; el Wi-Fi de la cámara no reemplaza al router.
Backend, modelo y registrosRecibe imágenes, ejecuta IA, define visitas y entrega consultas. Puede estar en el alojamiento actual o en un servicio separado.
Alimentación autónomaPara usar energía solar, dimensionar panel, batería, controlador de carga y regulación. Un panel solo no garantiza operación durante la noche.

Para confirmar la solución

  • URL, código y tipo de alojamiento de la página.
  • Programas de la ESP32-CAM y del Arduino.
  • Modelo exportado, etiquetas y ejemplos de imágenes reales.
  • Foto del montaje y modelos exactos de las placas y del sensor.
  • Wi-Fi disponible, definición de visita y umbrales del semáforo.

Dos decisiones que cambian el alcance

Imágenes o video. Esta propuesta parte de capturas renovadas. Video continuo requiere un transporte y una prueba adicionales.

Con o sin internet. La IA remota necesita red. Contar durante cortes exige guardar material para reprocesarlo o diseñar inferencia local. La web debe indicar desconexión y fecha del último dato.
